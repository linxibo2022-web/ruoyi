# /next - 下一步建议

作为项目开发顾问，综合分析项目全貌后，推荐**一个最优下一步**和备选方向。

---

## 第一步：收集项目全貌（5 个数据源，并行执行）

### 1.1 Git 提交分析（过滤非开发提交）

```bash
# 获取最近 10 条提交，包含 author/committer/message 信息
git log -10 --format="%H|%an|%cn|%s" --no-merges
```

**过滤规则**（以下提交不作为"最近在做什么"的判断依据）：

| 过滤条件 | 识别方式 | 分类 |
|---------|---------|------|
| Cherry-pick 提交 | commit message 包含 `cherry picked from` | 同步提交 |
| 上游同步提交 | commit message 以 `sync:` 或 `upstream:` 开头 | 同步提交 |
| Author ≠ Committer | author 和 committer 名字不同 | 可能是 cherry-pick |
| 文档/配置提交 | commit message 以 `docs:` `chore:` `style:` 开头 | 非功能提交 |

**输出**：
- 开发提交列表（排除同步/cherry-pick/docs 后的真正开发活动）
- 同步提交列表（单独标注，不影响建议方向）
- 最近开发方向判断（根据开发提交的 scope 和内容）

### 1.2 活跃任务文档（最重要的数据源）

```bash
# 扫描活跃任务
ls docs/tasks/active/
```

对每个活跃任务文档，**必须深度读取以下区域**：

| 读取区域 | 提取信息 | 用途 |
|---------|---------|------|
| 文件头部（状态/时间） | 状态（进行中/暂停）、最后更新时间 | 判断是否停滞 |
| 🎯 实现步骤 | `- [ ]` 和 `- [x]` 统计、下一个未完成步骤 | 计算进度、确定下一步 |
| 🔄 当前进度 | "正在进行"、"下一步操作"、"阻塞问题" | **直接作为推荐依据** |
| 🐛 问题记录 | 状态为 🔴 待解决 或 🟡 进行中的问题 | 判断是否有阻塞 |
| 📝 关键决策 | 技术选型、架构模式 | 理解任务上下文 |

**关键判断**：
- 如果任务有 "阻塞问题"（🔴 待解决）→ 推荐解决阻塞
- 如果任务 "下一步操作" 明确 → **直接推荐任务文档中的下一步**
- 如果任务超过 7 天未更新 → 提醒用户是否需要继续或暂停

### 1.3 待办清单

```bash
# 读取待办清单
Read docs/待办清单.md
```

提取：
- 高优先级待办数量和内容
- 中/低优先级待办概览
- 是否有逾期任务

### 1.4 需求文档

```bash
# 读取需求文档
Read docs/需求文档.md
```

提取：
- 状态为"待开发"或"开发中"的需求
- 需求的优先级排序

### 1.5 代码待办扫描

```bash
# 扫描 FIXME（紧急）
Grep pattern: "FIXME" path: ruoyi-modules/ glob: "*.java" output_mode: content -i

# 扫描 TODO（普通）
Grep pattern: "TODO" path: ruoyi-modules/ glob: "*.java" output_mode: count

# 前端/移动端也扫描
Grep pattern: "FIXME|TODO" path: plus-ui/src/ glob: "*.{vue,ts}" output_mode: count
Grep pattern: "FIXME|TODO" path: plus-uniapp/src/ glob: "*.{vue,ts}" output_mode: count
```

**注意**：如果 docs/ 下的某个文档不存在，跳过该数据源，不报错，不自动创建。

## 第二步：智能分析与排序

### 2.1 判断当前上下文

根据第一步收集的数据，判断用户当前所处的开发阶段：

| 信号 | 判断 |
|------|------|
| 有活跃任务文档且未完成 | **优先继续未完成任务** |
| 最近提交集中在某模块 | 建议在同模块继续延伸 |
| 待办清单有高优先级 | 优先推荐高优先级待办 |
| 有 FIXME 注释 | 优先修复 FIXME |
| 需求文档有"开发中"需求 | 优先完成进行中的需求 |

### 2.2 优先级排序规则

```
1. 🔴 活跃任务的阻塞问题（docs/tasks/active/ 中 🔴待解决 的问题）
2. 🟠 活跃任务的下一步（docs/tasks/active/ 中"下一步操作"或下一个未完成步骤）
     → 这是用户已明确跟踪的工作，有完整上下文，优先级最高
3. 🟡 阻塞性代码问题：FIXME、编译错误、安全漏洞
4. 🟢 高优先级待办（docs/待办清单.md 中的高优先级）
5. 🔵 需求文档中"待开发"的需求（按需求优先级）
6. ⚪ 代码 TODO 注释、低优先级待办
```

**核心理念**：活跃任务代表用户已投入时间和精力的进行中工作，中断后恢复的成本远高于开始新任务。因此除非有紧急阻塞，否则**始终优先推荐继续活跃任务**。

### 2.3 连贯性判断

**核心原则**：建议要和最近的开发活动连贯，避免跳跃。

- 如果最近在做模块 A 的功能，优先建议模块 A 的下一个任务
- 如果最近在修 Bug，优先建议相关的其他 Bug
- 如果任务刚完成，建议自然延伸（如：后端完成 → 前端页面 → 移动端适配）

## 第三步：输出建议

```markdown
# 下一步建议

## 当前状态

**最近开发活动**：
- {根据过滤后的 Git 提交，用 1-3 句话概括最近在做什么}

**同步提交**（不影响建议方向）：
- {如果有 cherry-pick/sync 提交，简要列出}
- {如果没有则省略此区域}

**活跃任务**：
- {docs/tasks/active/ 中的任务名称和进度，如果有}
- {如果没有则写"无活跃任务"}

**待办概览**：高 X 项 / 中 X 项 / 低 X 项
**FIXME**：X 处  **TODO**：X 处

---

## 推荐下一步

**{具体任务名称}**

- 来源：{活跃任务 / 待办清单 / 需求文档 / FIXME / 自然延续}
- 原因：{为什么推荐这个，1-2 句话}
- 位置：{涉及的模块/文件路径}
- 具体做什么：
  1. {步骤 1}
  2. {步骤 2}
  3. {步骤 3}

---

## 备选方向

1. **{备选任务 1}** — {一句话说明}
2. **{备选任务 2}** — {一句话说明}
3. **{备选任务 3}** — {一句话说明}

---

## 需要确认的问题（如有）

- {只在有不确定的决策时才列出}
```

---

## 强制规则

| 规则 | 说明 |
|------|------|
| 不预估时间 | 禁止输出"预计 X 小时/天" |
| 不给空泛建议 | 每条建议必须具体到模块/文件/操作 |
| 过滤 cherry-pick | cherry-pick/sync 提交不作为开发方向判断 |
| 读取任务和待办 | 必须尝试读取 docs/tasks/active/ 和 docs/待办清单.md |
| 一个推荐 + 备选 | 推荐区域只放一个最优建议，其他放备选 |
| 连贯性优先 | 未完成任务 > 新任务，同模块 > 跨模块 |
| 文档不存在时跳过 | 如果 docs/ 下文件不存在，跳过不报错 |
| 标注建议来源 | 每条建议标注数据来源（Git/任务/待办/需求/TODO） |

## 与其他命令的关系

| 命令 | 关系 |
|------|------|
| `/progress` | 全面进度报告（只读），/next 是精简的下一步建议 |
| `/update-status` | 更新文档，/next 只读取不修改 |
| `/add-todo` | 添加待办，/next 从待办中读取推荐 |
| `/dev` | 开始开发，/next 告诉你该开发什么 |
