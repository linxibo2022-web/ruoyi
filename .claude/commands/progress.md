# /progress - 项目进度报告

作为项目进度分析助手，综合分析项目全貌后，输出**结构化的全面进度报告**。

> **与 /next 的区别**：/progress 是全面的只读报告（当前状态的快照），/next 是精简的下一步建议。

---

## 第一步：收集项目全貌（6 个数据源，并行执行）

### 1.1 Git 提交分析（过滤非开发提交）

```bash
# 获取最近 20 条提交，包含 author/committer/message 信息
git log -20 --format="%H|%an|%cn|%s" --no-merges
```

**过滤规则**（以下提交不计入开发活动统计）：

| 过滤条件 | 识别方式 | 分类 |
|---------|---------|------|
| Cherry-pick 提交 | commit message 包含 `cherry picked from` | 同步提交 |
| 上游同步提交 | commit message 以 `sync:` 或 `upstream:` 开头 | 同步提交 |
| Author ≠ Committer | author 和 committer 名字不同 | 可能是 cherry-pick |
| 文档/配置提交 | commit message 以 `docs:` `chore:` `style:` 开头 | 非功能提交 |

**输出**：
- 开发提交数量和列表（过滤后）
- 同步提交数量（单独统计）
- 非功能提交数量（docs/chore/style）
- 最近开发方向（根据 commit scope 归类）

### 1.2 活跃任务文档

```bash
# 扫描活跃任务
ls docs/tasks/active/
```

对每个活跃任务文档，**必须读取以下区域**：

| 读取区域 | 提取信息 | 用途 |
|---------|---------|------|
| 文件头部（状态/时间） | 状态（进行中/暂停）、最后更新时间 | 判断是否停滞 |
| 🎯 实现步骤 | `- [ ]` 和 `- [x]` 统计 | 计算步骤完成率 |
| 🔄 当前进度 | "正在进行"、"下一步操作"、"阻塞问题" | 汇总当前状态 |
| 🐛 问题记录 | 各状态（🟢已解决/🟡进行中/🔴待解决）数量 | 问题统计 |

**关键判断**：
- 任务超过 7 天未更新 → 标记为"⚠️ 可能停滞"
- 任务有 🔴 待解决问题 → 标记为"🔴 有阻塞"

### 1.3 待办清单

```bash
# 读取待办清单
Read docs/待办清单.md
```

提取：
- 高/中/低优先级待办数量
- 已完成待办数量（如果有"最近完成"区域）
- 逾期任务数量

### 1.4 需求文档

```bash
# 读取需求文档
Read docs/需求文档.md
```

提取：
- 各状态的需求数量：已完成、开发中、待开发、已搁置
- 需求完成率

### 1.5 代码模块扫描

**按 Maven 模块统计**：
- 扫描 `ruoyi-modules/ruoyi-*`（排除 common/admin/extend）
- 对每个业务模块，统计已实现的功能数量
- 检查模块完整性：Controller + Service + DAO + Mapper + Entity

**前端页面统计**：
- 扫描 `plus-ui/src/views/business/` 下的页面数量
- 扫描 `plus-uniapp/src/pages/` 和 `plus-uniapp/src/pages-sub/` 下的页面数量

### 1.6 代码待办扫描

```bash
# 扫描 FIXME（紧急）
Grep pattern: "FIXME" path: ruoyi-modules/ glob: "*.java" output_mode: count

# 扫描 TODO（普通）
Grep pattern: "TODO" path: ruoyi-modules/ glob: "*.java" output_mode: count

# 前端/移动端也扫描
Grep pattern: "FIXME|TODO" path: plus-ui/src/ glob: "*.{vue,ts}" output_mode: count
Grep pattern: "FIXME|TODO" path: plus-uniapp/src/ glob: "*.{vue,ts}" output_mode: count
```

**注意**：如果 docs/ 下的某个文档不存在，跳过该数据源，不报错，不自动创建。

## 第二步：综合分析

### 2.1 开发活跃度分析

根据过滤后的 Git 提交：
- 最近 7 天的提交频率
- 主要开发方向（按 commit scope 分组）
- 开发节奏判断（活跃/平稳/停滞）

### 2.2 任务健康度分析

| 指标 | 健康 | 警告 | 危险 |
|------|------|------|------|
| 活跃任务更新间隔 | < 3 天 | 3-7 天 | > 7 天 |
| 阻塞问题数 | 0 | 1 | > 1 |
| 待办积压趋势 | 减少 | 持平 | 增加 |

### 2.3 完成度计算

```
模块完成度 = 已完成功能数 / (已完成 + 进行中 + 待开发) × 100%
需求完成率 = 已完成需求数 / 总需求数 × 100%
待办消化率 = 已完成待办数 / (已完成 + 未完成) × 100%（如果有数据）
```

## 强制规则

| 规则 | 说明 |
|------|------|
| 不预估时间 | 禁止输出"预计 X 小时/天" |
| 只读不写 | /progress 只分析和输出报告，不修改任何文件 |
| 过滤 cherry-pick | cherry-pick/sync 提交不计入开发活动统计 |
| 读取活跃任务 | 必须尝试读取 docs/tasks/active/ |
| 读取待办和需求 | 必须尝试读取 docs/待办清单.md 和 docs/需求文档.md |
| 文档不存在时跳过 | 如果 docs/ 下文件不存在，跳过不报错，不自动创建 |
| 客观评估 | 给出客观的进度评估，不夸大不缩小 |
| 结尾联动 | 报告末尾必须推荐运行 /next |

---

## 与其他命令的关系

| 命令 | 关系 |
|------|------|
| `/next` | /progress 是全面报告，/next 是精简的下一步建议 |
| `/update-status` | /update-status 会修改文档，/progress 只读 |
| `/check` | /check 检查代码规范，/progress 统计代码质量指标 |
| `/start` | /start 是新窗口快速概览，/progress 是深度进度报告 |
