
# 方案评审技能（Design Review）

## 概述

本技能在方案/设计文档完成后执行**对抗性审查**，目的是在编码开始前发现漏洞、遗漏和不一致。区别于 `brainstorm`（发散方案）和 `tech-decision`（技术选型），本技能专注于**已定方案的质量把关**。

> **核心定位**：`brainstorm` → 产生方案 → **`design-review`（本技能）**→ 通过评审 → `writing-plans` → 执行

**与相邻技能的边界**：
- 「还没定方案，要讨论怎么做」→ `brainstorm`
- 「两个技术选哪个」→ `tech-decision`
- 「方案定了，要评审把关」→ **`design-review`（本技能）**
- 「代码写好了，要审代码」→ `/code-review`（内置命令）
- 「排查已发生的 Bug」→ `bug-detective`

---

## 一、评审原则

### 1.1 评审纪律

- 🔴 **不找茬**：不是为了说方案不好，而是让方案更稳
- 🔴 **证据驱动**：每个问题必须带"为什么这是问题"+"什么情况下会出问题"
- 🔴 **分级输出**：严重问题（阻塞）/ 中等问题（建议修）/ 轻微问题（可忽略）
- 🔴 **不带方案**：只指出问题，不强行给替代方案（除非用户要求）

### 1.2 评审范围

| 评审对象 | 输入格式 | 典型场景 |
|---------|---------|---------|
| 头脑风暴结论 | `docs/brainstorm-*.md` | 方案选定后、实施前检查 |
| 架构设计 | 设计文档 / 口头描述 | 模块划分、技术选型后 |
| 实施计划 | `docs/tasks/active/*.md` | 任务拆解后、执行前检查 |
| 需求文档 | `docs/需求文档.md` | 需求确认后、开发前 |

## 二、评审框架（11 维度）

### 维度 1：功能完整性
| 检查点 | 问什么 |
|--------|--------|
| 正常路径 | 主流程每一步是否都覆盖了？有没有跳过的环节？ |
| 异常路径 | 每个外部依赖失败时会发生什么？(DB/Redis/MQ/第三方API) |
| 边界条件 | 空值、超长值、并发、极限数量时的行为？ |
| 权限边界 | 不同角色看到的是否一样？未登录/无权限时怎么处理？ |
| 状态流转 | 所有状态之间的跳转是否都定义了？有没有死锁状态？ |

### 维度 2：多租户
| 检查点 | 问什么 |
|--------|--------|
| 数据隔离 | 新表是否继承 `TenantEntity`？查询是否会自动过滤 `tenant_id`？ |
| 配置归属 | 配置是系统级还是租户级？不同租户能否独立定制？ |
| 数据混入 | 会不会出现租户 A 看到租户 B 的数据？缓存 key 是否含租户 ID？ |

### 维度 3：多数据库兼容
| 检查点 | 问什么 |
|--------|--------|
| 类型匹配 | String 类型用 `like()`，非 String 用 `likeCast()` |
| 函数兼容 | SQL 中是否用了特定数据库的函数？(如 MySQL 的 `DATE_FORMAT`) |
| 分页兼容 | 分页语法是否适配所有目标数据库？ |

### 维度 4：性能与扩展
| 检查点 | 问什么 |
|--------|--------|
| 查询性能 | 是否有 N+1 查询？列表是否做了分页？大表是否有索引？ |
| 缓存策略 | 热点数据是否缓存？缓存过期策略是否合理？缓存穿透/雪崩怎么防？ |
| 并发控制 | 库存/余额等资源是否有并发控制？用的是乐观锁还是分布式锁？ |
| 数据量 | 表预计数据量多大？是否需要分区/分表？ |

### 维度 5：安全
| 检查点 | 问什么 |
|--------|--------|
| 输入校验 | 所有用户输入是否在后端做了校验？有没有仅前端校验的情况？ |
| SQL 注入 | 动态 SQL 拼接是否安全？ |
| 敏感数据 | 密码/手机号/身份证是否脱敏？日志里会不会打印敏感信息？ |
| 权限校验 | 每个接口是否都有权限注解？是否校验了数据权限？ |

### 维度 6：API 设计规范
| 检查点 | 问什么 |
|--------|--------|
| 路径规范 | 是否符合 `/pageXxxs`、`/getXxx/{id}`、`/addXxx` 格式？ |
| 请求方法 | GET/POST/PUT/DELETE 是否使用正确？ |
| 响应格式 | 是否统一使用 `R<T>` 包装？ |
| 参数命名 | 是否使用驼峰命名？与项目已有 API 风格一致？ |

### 维度 7：数据库设计
| 检查点 | 问什么 |
|--------|--------|
| 表前缀 | 表前缀是否匹配模块（b_/m_/crm_/iot_/sys_）？ |
| 主键策略 | 是否使用雪花 ID？(不是 AUTO_INCREMENT) |
| 审计字段 | 是否包含 create_dept/create_by/create_time/update_by/update_time/remark/is_deleted？ |
| 字段命名 | 手机号是否用 `phone`(不是 `phonenumber`)？删除标记是否用 `is_deleted`(不是 `del_flag`)？ |

### 维度 8：代码生成适配
| 检查点 | 问什么 |
|--------|--------|
| 模板可用 | BO/VO/Service/DAO/Controller 是否能用标准模板生成？ |
| 自定义逻辑 | 哪些地方需要手写?能否明确标注？ |
| 测试覆盖 | 方案中是否考虑了测试？ServiceTest/ControllerTest/E2E 是否都覆盖到？ |

### 维度 9：前后端对接
| 检查点 | 问什么 |
|--------|--------|
| 类型一致 | Long 型 ID 前端是否正确处理？是否有精度丢失风险？ |
| 字典翻译 | 字典值是在后端翻译还是前端翻译？有没有遗漏的字典列？ |
| 文件上传 | 文件上传路径/大小限制/格式限制是否约定清楚？ |

### 维度 10：运维与部署
| 检查点 | 问什么 |
|--------|--------|
| 初始化数据 | 是否需要菜单 SQL？是否需要字典数据？是否需要默认配置？ |
| 版本兼容 | 新表/新字段是否影响已有功能？是否需要数据迁移？ |
| 回滚方案 | 如果新功能出问题，能否快速回滚？ |

### 维度 11：实施风险
| 检查点 | 问什么 |
|--------|--------|
| 依赖顺序 | 是否依赖其他未完成的模块？是否需要先做某个基础功能？ |
| 技术难度 | 是否有团队不熟悉的技术？是否需要提前验证？ |
| 时间风险 | 是否低估了某个环节的工作量？ |

## 三、评审输出格式

### 3.1 评审报告模板

```markdown
# 方案评审报告：{方案名称}

**评审时间**: {东八区时间}
**评审对象**: {文档路径或方案描述}
**评审结论**: 🟢 通过 | 🟡 有条件通过 | 🔴 需修改

---

## 严重问题（阻塞，必须修改）

| 编号 | 维度 | 问题描述 | 影响 | 建议 |
|------|------|---------|------|------|
| S1 | 多租户 | xxx | xxx | xxx |

## 中等问题（建议修改）

| 编号 | 维度 | 问题描述 | 影响 | 建议 |
|------|------|---------|------|------|
| M1 | 性能 | xxx | xxx | xxx |

## 轻微问题（可忽略）

| 编号 | 维度 | 问题描述 |
|------|------|---------|
| L1 | 代码风格 | xxx |

## 维度覆盖总览

| 维度 | 结果 | 备注 |
|------|:---:|------|
| 功能完整性 | ✅ | |
| 多租户 | ⚠️ | 缺租户隔离 |
| 多数据库 | ✅ | |
| 性能与扩展 | ✅ | |
| 安全 | ⚠️ | 缺输入校验 |
| API 设计 | ✅ | |
| 数据库设计 | ✅ | |
| 代码生成 | ✅ | |
| 前后端对接 | ❌ | Long 精度未处理 |
| 运维与部署 | ✅ | |
| 实施风险 | ✅ | |

## 评审总结

共发现 S×N 个严重问题, M×N 个中等问题, L×N 个轻微问题。
{一句话总结}
```

### 3.2 评审结论定义

| 结论 | 含义 |
|------|------|
| 🟢 通过 | 没有严重/中等问题，可以直接实施 |
| 🟡 有条件通过 | 有中等问题但不阻塞，建议修改后实施 |
| 🔴 需修改 | 有严重问题，必须先改方案再实施 |

## 四、使用方式

### 4.1 评审单个方案文档

```
用户: "评审一下 docs/brainstorm-测试自动生成.md"

→ 读取文档 → 按 11 维度逐项审查 → 输出评审报告
```

### 4.2 评审当前方案（无文档）

```
用户: "刚才讨论的方案过一遍，看看有什么遗漏"

→ 基于对话历史中的方案内容 → 逐维度审查 → 输出评审报告
```

### 4.3 快速检查（仅严重问题）

```
用户: "快速过一下数据库设计有没有问题"

→ 仅检查维度 7（数据库设计）+ 维度 2（多租户）→ 只输出严重/中等问题
```

## 五、常见问题

### Q1: design-review 和 code-review 有什么区别？

- **design-review**: 设计方案阶段，还没写代码。审的是"想法对不对"
- **code-review**: 代码已写完。审的是"代码写得对不对"

### Q2: design-review 和 brainstorm 有什么区别？

- **brainstorm**: 发散阶段，产生多个方案选项。审的是"有哪几种可能"
- **design-review**: 收敛阶段，验证已选方案。审的是"这个方案有没有漏洞"

### Q3: 评审一定要覆盖 11 个维度吗？

不需要。根据方案类型选择相关维度：
- 数据库设计 → 侧重维度 2/3/7
- API 设计 → 侧重维度 5/6/9
- 架构设计 → 侧重维度 1/4/8/10/11
- 全栈方案 → 11 个维度全过

### Q4: 评审发现问题后要不要给替代方案？

默认只指出问题和建议方向，不完整设计替代方案。如果用户说"那该怎么改"，再展开讨论。
