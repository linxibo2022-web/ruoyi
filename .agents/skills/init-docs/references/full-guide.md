
# /init-docs - 初始化业务文档

作为项目文档初始化助手，根据用户选择的模式初始化项目文档。

支持三种使用方式：
- `/init-docs` — 交互式选择模式
- `/init-docs 实现用户反馈管理功能` — 基于描述智能初始化
- `/init-docs docs/brainstorm-用户反馈.md` — 基于需求文档智能初始化

---

## 🔍 第零步：参数检测（在模式选择前执行）

检查用户是否在 `/init-docs` 后附带了参数。

### 检测规则

| 参数类型 | 判断条件 | 处理方式 |
|---------|---------|---------|
| **无参数** | `/init-docs` 后无内容 | → 进入第一步（交互式选择模式） |
| **文件路径** | 参数以 `.md` 结尾，或包含 `/` 或 `\` 路径分隔符 | → 进入**模式三：基于需求文档初始化** |
| **文本描述** | 其他情况（中文描述、功能名称等） | → 进入**模式三：基于描述初始化** |

### 文件路径检测

如果参数看起来像文件路径：
1. 检查文件是否存在
2. 如果存在 → 读取文件内容，进入模式三
3. 如果不存在 → 提示文件未找到，建议：
   ```
   未找到文件：{路径}

   你可以：
   1. 先运行头脑风暴生成需求文档：直接描述你想实现的功能
   2. 直接用描述初始化：/init-docs {功能描述}
   3. 交互式选择模式：/init-docs
   ```

## 🎯 第一步：询问用户选择模式

> **注意**：仅在无参数时执行此步骤。有参数时直接跳到模式三。

### 上下文智能检测

在展示选项前，先检查**当前对话上下文**：

- 如果当前对话中**已经进行过头脑风暴**（对话中包含"方案设计"、"方案对比"、"推荐方案"、"实施步骤"等标题，或之前激活过 brainstorm 技能），则**自动推荐模式三**：
  ```
  检测到当前对话中有头脑风暴产出的方案设计。

  是否基于该方案直接初始化项目文档？（推荐）
  - 输入"是"或"确认" → 进入模式三，自动提取头脑风暴结论
  - 输入"否" → 显示完整模式选择菜单
  ```
  如果用户确认 → 直接进入模式三，从当前对话上下文提取头脑风暴结论作为输入。

- 如果当前对话**没有头脑风暴产出** → 正常展示模式选择菜单。

### 模式选择菜单

**向用户展示以下选项：**


### 2. 智能识别业务模块结构

#### 第一步：识别业务 Maven 模块
**扫描路径**: `ruoyi-modules/`

**识别规则**:
1. 列出 `ruoyi-modules/` 下的所有 `ruoyi-*` 目录
2. **根据 framework-config.json 排除框架模块**：
   - ❌ `ruoyi-system` - 系统管理模块（29个功能，框架提供）
   - ❌ `ruoyi-generator` - 代码生成器（框架提供）
3. **业务模块示例**：
   - ✅ `ruoyi-business` - 基础业务模块
   - ✅ `ruoyi-iot` - IoT 设备管理模块
   - ✅ `ruoyi-mall` - 商城模块
   - ✅ `ruoyi-crm` - CRM 模块
   - ✅ `ruoyi-erp` - ERP 模块
   - ✅ 其他自定义业务模块

**判断标准**：
```
业务模块特征：
1. 位于 ruoyi-modules/ruoyi-* 目录
2. 不在框架模块排除列表中
3. 包含 src/main/java/plus/ruoyi/{模块名}/ 目录
4. 有 controller、service、dao、domain 等包结构
```

**特别注意**：
- 如果检测到 0 个业务模块 → 这是全新项目，生成空的业务文档模板
- 提示用户："当前是全新框架，尚无业务代码。开发业务功能后再次执行本命令更新文档。"

#### 第二步：分析每个业务模块的内部结构

对每个识别出的业务模块（如 `ruoyi-business`、`ruoyi-iot`）：

##### 方式A：单层结构（直接包含 controller）
```
ruoyi-iot/
└── src/main/java/plus/ruoyi/iot/
    ├── controller/
    │   ├── DeviceController.java
    │   ├── ProductController.java
    │   └── OtaController.java
    ├── service/
    ├── dao/
    └── domain/
```
**识别方式**：直接统计 controller 数量，每个 Controller = 一个功能模块

##### 方式B：多层结构（按业务领域分包）
```
ruoyi-business/
└── src/main/java/plus/ruoyi/business/
    ├── ai/
    │   ├── controller/
    │   ├── service/
    │   ├── dao/
    │   └── domain/
    ├── base/
    │   ├── controller/
    │   └── ...
    └── platform/
        ├── controller/
        └── ...
```
**识别方式**：
1. 识别子包目录（ai、base、platform 等）
2. 每个子包代表一个业务领域
3. 统计每个子包下的 Controller 数量

**自动判断使用哪种方式**：
- 如果 `src/main/java/plus/ruoyi/{模块名}/` 下直接有 `controller/` 目录 → 使用方式A
- 如果下面还有子目录（如 ai/、base/），且子目录下有 `controller/` → 使用方式B

#### 第三步：统计功能模块完整性

对每个 Controller，检查对应的文件完整性：
```
示例：DeviceController.java

检查以下文件是否存在：
- Entity: Device.java (domain/*.java)
- BO: DeviceBo.java (domain/bo/*.java)
- VO: DeviceVo.java (domain/vo/*.java)
- Service 接口: IDeviceService.java (service/I*Service.java)
- Service 实现: DeviceServiceImpl.java (service/impl/*ServiceImpl.java)
- DAO 接口: IDeviceDao.java (dao/I*Dao.java)
- DAO 实现: DeviceDaoImpl.java (dao/impl/*DaoImpl.java)
- Mapper: DeviceMapper.java (mapper/*Mapper.java)

完整度计算：存在的文件数 / 8 * 100%
```

### 4. 智能分析 Git 提交

**分析最近 20-30 条提交**:
1. 提取提交信息、日期、修改的文件
2. **区分框架提交 vs 业务提交**：
   - 框架提交：修改 `ruoyi-common/`、`ruoyi-admin/`、`ruoyi-extend/` 或系统管理相关代码
   - 业务提交：修改业务模块代码
3. **提取业务功能的提交信息**：
   - 识别关键词：`feat`、`fix`、`update`、`add`、`implement`
   - 提取功能描述
4. **计算开发耗时**：
   - 根据同一模块的首次提交和最后提交计算
5. **识别最近开发的模块**：
   - 按提交频率排序
   - 标注最活跃的业务模块

**业务提交识别规则**:
```
包含以下路径之一：
- ruoyi-modules/ruoyi-business/
- ruoyi-modules/ruoyi-iot/
- ruoyi-modules/ruoyi-mall/
- ruoyi-modules/ruoyi-ai/
- ruoyi-modules/ruoyi-*/（排除 ruoyi-common、ruoyi-admin、ruoyi-extend）
- plus-ui/src/views/（排除 system、monitor、tool）
- plus-ui/src/api/（排除系统 API）
- plus-uniapp/src/pages-sub/

或包含以下 commit 前缀：
- feat(业务模块名):
- fix(业务模块名):
- update(业务模块名):
```

## 📏 质量标准

### ✅ 优秀文档的特征
1. **完整度明确**: 用百分比表示，不模糊
2. **代码定位精确**: 完整的相对路径 + 行号
3. **工作量合理**: 根据 Git 提交历史估算
4. **分类清晰**:
   - 一级分类：按 Maven 模块（ruoyi-iot、ruoyi-mall、ruoyi-business）
   - 二级分类：按业务领域（仅当模块内有子包时）
5. **信息完整**: 包含依赖、影响范围、解决方案
6. **统计准确**: 数量、百分比、工作量都有数据支撑

### ❌ 必须避免的问题
1. **不要统计框架代码**: 只关注业务 Maven 模块（排除 ruoyi-common、ruoyi-admin、ruoyi-extend）
2. **不要只统计文件数**: 要分析功能完整度
3. **不要笼统描述**: "XX 模块已完成" → "XX 模块 100% (Entity✅ BO✅ VO✅...)"
4. **不要遗漏 TODO**: 深度扫描所有业务模块代码中的 TODO 标记
5. **不要估算过于乐观**: 工作量评估要参考历史提交
6. **不要忽略技术债务**: 单独列出 FIXME 和已知问题
7. **不要混淆模块层级**:
   - Maven 模块（ruoyi-iot）是顶层

```
将基于这些信息生成预填充文档。是否确认？

```

```
AI:

**端支持**: PC + 移动端
**推荐方案**: 方案 A - 复用现有投诉模块
**实施步骤**: 6 个
**风险项**: 2 个

是否基于这些信息生成项目文档？

用户: 确认

AI:
✅ 基于头脑风暴输出初始化完成！

📁 已创建 3 个文档，包含完整的需求、方案和待办信息。
💡 建议运行 `/dev` 开始开发第一步：设计数据库表结构
```

### 与头脑风暴的完整联动流程

```
1. 用户进行头脑风暴
   用户: "帮我想想怎么做用户反馈功能"
   → 激活 brainstorm 技能
   → 输出方案设计

2. 头脑风暴完成后建议保存
   AI: "💡 建议运行 /init-docs 实现用户反馈管理功能"

3. 用户执行 init-docs
   用户: /init-docs 实现用户反馈管理功能
   → 进入模式三
   → 基于上下文（当前对话中的头脑风暴结论）智能预填充
   → 生成预填充的项目文档

4. 用户开始开发
   用户: /dev
   → 读取 docs/ 中的文档
   → 基于已有方案开始编码
```

> **注意**：当从头脑风暴直接进入 init-docs 时（同一对话上下文），应该利用当前对话中的头脑风暴结论来预填充文档，而不仅仅依赖用户输入的描述文本
