# 头脑风暴：新模块自动生成测试

**创建时间**: 2026-08-12
**最后更新**: 2026-08-12
**状态**: 已确定方案（评审通过，有条件）

---

## 背景与目标

用 `/dev` 或 `/crud` 生成新模块时，自动生成对应的测试文件，消除"手写测试实例"的额外工作。让 `mvn test` 和 `pnpm test:unit` 在模块生成后即可运行，无需手动补充。

---

## 方案讨论

### 方案 A：纯文档驱动（选定）

在 `/dev`、`/crud` 命令文档中追加测试生成步骤，AI 按文档指令参照已有模板直接写测试代码。新增 `/add-test` 命令供独立补测试场景。

### 方案 B：Velocity 模板驱动

在 ruoyi-generator 模块新增 `.vm` 模板，扩展 `VelocityUtils`，前后端测试均通过模板引擎生成。

### 方案 C：混合方案

后端测试用 Velocity（确定性高），前端 Vitest + E2E 用 AI（灵活性）。

### 选择方案 A 的理由

1. **改动最小**：只改 4 个 Markdown 文件，零 Java 改动，零编译
2. **与现有体系一致**：`/dev` 和 `/crud` 本身就是文档驱动，AI 已在生成 13 个 Java/TS 文件，多加 2~4 个测试文件属同质工作
3. **后端测试模板化程度极高**：ServiceTest 就是增删改查分页五个操作，ControllerTest 就是六个 HTTP 端点，AI 参照模板做类名/路径替换，不会写歪
4. **前端 Vitest 需要灵活性**：只有存在自定义逻辑时才生成，Velocity 模板做不了"扫描代码做智能判断"
5. **无需维护 VM 模板**：VM 模板需要和代码同步维护，文档驱动的规则调整只需改文档

## 最终结论

### 整体架构

```
/dev 或 /crud 生成 13 个业务文件后
    │
    ├── 【自动·必生成】后端 ServiceTest.java
    │       参照 AdServiceTest 模板，替换类名/包名/字段
    │       add / page / get / update / delete 五个方法
    │
    ├── 【自动·必生成】后端 ControllerTest.java
    │       按 API 路径规范，测试六个端点
    │       doGet / doPost / doPut / doDelete
    │
    ├── 【自动·必追加】E2E crud-smoke.spec.ts
    │       向 CRUD_PAGES 数组 push 一行配置
    │       追加前去重（apiAdd 字段唯一性校验）
    │
    └── 【智能·按需】前端 Vitest
            扫描 V1~V5 条件，有则生成，无则跳过
            ┌─ V1: composables/useXxx.ts 存在 → 生成测试
            ├─ V2: utils/xxx.ts exports ≥1 → 生成测试
            ├─ V3: Store 有非通用 action → 生成测试
            ├─ V4: ServiceImpl 方法 >6 → 追加自定义逻辑段
            └─ V5: Vue computed ≥3 → 提醒提取 composable
```

### 触发入口

| 入口 | 何时用 | 行为 |
|------|--------|------|
| `/dev` | 新模块从零开发 | 步骤 7 末尾自动触发 |
| `/crud` | 已有表补代码 | 步骤 5 末尾自动触发 |
| `/add-test 模块名` | 已有模块补测试 | 独立执行检测 + 生成（支持增量：用户后续写了 composable 再调） |

|------|:---:|------|

### 🔴 防护规则（评审 S1/S2 修复）

**S1 — 防重复覆盖**：
- 所有自动生成的测试文件**第一行**加入标记注释：
  ```java
  // @Generated by /dev — 请勿删除此行，手动修改请在标记行之后进行
  ```
- 生成前检查目标文件是否存在，若存在且包含 `@Generated` 行 → **仅更新标记行之后的自动生成段**，保留手写部分
- 若存在但不含标记 → 跳过生成，提示用户"文件已存在且非自动生成，手动检查后决定"

**S2 — E2E 去重**：
- 追加 `CRUD_PAGES` 配置前，读取 `crud-smoke.spec.ts`，用 `apiAdd` 字段做唯一性校验
- 已存在 → 跳过，提示"E2E 配置已存在，无需重复追加"
- 不存在 → 追加到数组末尾

### Vitest 检测规则（量化标准）

| 编号 | 条件 | 检测方式 | 生成什么 |
|:---:|------|---------|------|
| V1 | **存在自定义 composable** | 文件 `src/composables/use{Module}.ts` 存在 | `use{Module}.test.ts` |
| V2 | **存在模块 utils** | 文件 `src/utils/{module}.ts` 存在且 exports ≥ 1 个函数 | `{module}.test.ts`（每个 export 一个 describe） |
| V3 | **Store 有自定义 action** | `src/store/modules/{module}.ts` 中存在非通用 CRUD 的 action | `{module}Store.test.ts`（只测自定义 action） |
| V4 | **ServiceImpl 有自定义方法** | `XxxServiceImpl.java` 中方法数 > 6 | 在 ServiceTest 中追加"自定义业务逻辑"测试段 |
| V5 | **Vue 页面有计算属性** | `.vue` 中 `computed` 数量 ≥ 3 | 提示提取为 composable，不自动生成（需人工先重构） |

> ⚠️ **重要**：V1~V3 依赖 composables/utils/store 文件已存在。`/dev` 本身不生成这些文件，所以 **`/dev` 时 V1~V3 几乎不会触发**。正确使用方式：写完 composable 后单独调 `/add-test 模块名` 做增量补测。`/check` 也会提示可补测项。

### 租户处理（评审 M5 修复）

- ServiceTest 模板的 `@BeforeEach` 中显式设置租户：
  ```java
  @BeforeEach
  void setUp() {
      TenantHelper.setTenantId("000000");
  }
  ```

### 生成后处理

- 生成完成后提示用户："已生成 X 个测试文件。建议先 `mvn test -Dtest=XxxServiceTest` 跑通后提交"
- 不自动 `git add`，由用户确认后手动提交

## 风险与注意事项

| 风险 | 应对策略 |
|------|---------|
| AI 生成的测试代码字段名不匹配 | `/dev` 流程要求 AI 从已生成的 Entity 读取字段名再填模板 |
| 长对话中 AI 丢失上下文参数 | `/dev` 和 `/crud` 文档中要求测试生成前重新确认模块名/包路径/API 前缀 |
| 旧项目已有手写测试，新模板不兼容 | `@Generated` 标记行机制确保不覆盖手写文件 |
| V1~V3 在 `/dev` 时几乎不触发 | `/add-test` 支持增量检测；`/check` 提示可补测项 |
| E2E 配置重复 | `apiAdd` 唯一性校验 |
| 多租户数据混入 | 模板 `@BeforeEach` 显式设置 `tenant_id` |

- 确定不自动生成前端 Vitest 用于标准 CRUD 模块（无业务逻辑可测）
