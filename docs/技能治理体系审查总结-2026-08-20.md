## 一、结论速览

**整体判断：核心治理链路已经成立，当前主要风险不在“机制是否存在”，而在“说明、校验器与实际来源模型是否完全一致”。**

本轮确认 2 个 P1、4 个 P2 和 5 个 P3 问题：

- **P1：治理说明仍有旧模型残留；中央校验器对命令映射的覆盖与文档承诺不一致。**
- **P2：命令拆分脚本存在未显式授权的反向覆盖路径；`framework-sync` 身份模型不明确；Claude `Edit` 未进入敏感文件提醒；共享计划技能缺少 Goal 能力降级约定。**
- **P3：必需依赖缺少绝对上限、双端路由提示格式不一致、索引固定截断、短入口同质化，以及 SessionStart 仅存在潜在差异。**

原文中以下结论需要纠正：

1. Codex 当前具备 Goal 能力，不能再写成“Codex 端没有 Goal、该章节是死指令”。
2. 命令映射数量是 **16 个**，不是 15 个。
3. `split-command-mapped-entries.cjs` 不会无条件创建 `framework-sync` 的双重身份；它会在共享目录已经存在时将 Codex 技能包反向覆盖到 Claude 技能目录。
4. `framework-sync` 并未形成“两套校验器都完全看不到”的整体盲区；准确说法是两个校验器采用了不同身份分支，单独运行其中一个时覆盖不完整。
5. `writing-plans` 的完整资料当前恰好有 16 个二级标题，没有被截断；实际被截断的是另外 11 个共享技能和 3 个命令资料入口。

## 四、问题明细

### 4.1 P1：两处完整资料残留旧登记模型

以下内容仍要求手工修改 Hook 技能列表或根规则技能表：

- `.claude/skills/writing-plans/references/full-guide.md:363`
- `.claude/skills/exp-sediment/references/full-guide.md:417-418`

它们与当前治理模型直接矛盾：

- 自动路由应登记到 `.agent-governance/skills-manifest.json`。
- 公共根规则应修改 `.agent-governance/core-rules.md` 或模板，再由 `sync-agent-assets.cjs` 渲染。
- `.claude/hooks/skill-forced-eval.cjs` 不再维护技能清单。
- `AGENTS.md`、`CLAUDE.md` 是生成结果，不应手工维护技能表。

这不是措辞问题，而是会引导维护者修改错误的真相源，属于必须优先清理的内容漂移。

### 4.2 P1：中央校验器只校验 `dev` 命令映射

`add-skill/references/full-guide.md` 将 `.agent-governance/scripts/verify-agent-assets.cjs` 描述为技能、根规则和命令映射的一致性验收入口，但当前脚本的命令映射校验只硬编码了：

```text
.claude/commands/dev.md
↔ .agents/skills/dev/SKILL.md
```

其余 15 个命令映射由 `skill-check.cjs` 覆盖，但 `add-skill` 的默认验收命令并未调用 `skill-check.cjs`。因此，仅执行 `add-skill` 文档列出的验收链时，非 `dev` 命令映射可能在不一致的情况下漏检。

建议让 `verify-agent-assets.cjs` 从 `skill-sync-policy.json.commandMappings` 动态遍历全部映射，或把 `skill-check.cjs` 明确纳入 `add-skill` 的强制验收；不应继续保留“文档承诺全量、脚本实际单例”的状态。

### 4.3 P2：命令拆分脚本存在反向覆盖共享源的路径

`.claude/skills/add-skill/scripts/split-command-mapped-entries.cjs` 以 Codex Skill 为命令映射迁移基准。对于已存在同名 Claude 共享技能目录的条目，脚本还会执行：

```text
删除 .claude/skills/<name>/
再从 .agents/skills/<name>/ 复制回来
```

当前只有 `framework-sync` 命中该分支。风险不在“脚本会主动创建重叠身份”，而在“重叠身份一旦存在，脚本会无参数、无差异确认地反向覆盖 Claude 技能目录”，这与常规维护默认以 Claude 技能目录为内容源的规则冲突。

建议对该分支采用以下任一明确策略：

- 双重身份不被允许：检测到同名共享目录后立即失败，要求先完成身份裁决。
- 双重身份被允许：在策略文件显式声明，并要求调用方明确选择基准端，禁止静默 `rmSync + cpSync`。

### 4.4 P2：`framework-sync` 的身份模型不唯一

`framework-sync` 同时存在于：

- `.claude/skills/framework-sync/`
- `.claude/commands/framework-sync.md`
- `.agents/skills/framework-sync/`
- `skill-sync-policy.json.commandMappings`

这可能是有意提供 `$framework-sync` 与 `/framework-sync` 两个 Claude 入口，也可能是迁移遗留；仅凭当前代码不能直接断言应该删除哪一端。

当前校验行为也因此分叉：

- `verify-agent-assets.cjs` 按“共享技能”比较 Claude/Codex 完整包。
- `skill-check.cjs` 因命令映射优先，按“命令映射”比较 Claude Command/Codex Skill 正文，不再比较该条目的共享技能包。

两个校验器一起运行时能够覆盖两种关系；单独运行 `skill-check.cjs` 时看不到 `framework-sync` 的共享包差异，单独运行 `verify-agent-assets.cjs` 时看不到其命令映射关系（除硬编码的 `dev` 外）。应先明确它是“命令映射”“共享技能”还是“显式允许的双入口”，再让两个校验器遵循同一身份声明。

### 4.5 P2：共享计划技能缺少 Goal 能力降级约定

项目中没有独立的 `goal` 技能；`plan-executor/references/full-guide.md` 的“Goal 协作”依赖宿主运行时提供 Goal 能力。

原文将其描述为“Claude Code 有、Codex 没有”，该判断已经失真：当前 Codex 运行时提供 Goal 状态能力，官方文档也提供 `/goal` 工作流。真正的问题是共享技能没有定义能力探测和降级规则。

建议改为运行时无关的约定：

- 宿主提供 Goal 时，可用 Goal 追踪整个计划，但完成判据仍是任务全部 `[x]` 且全局验收通过。
- 宿主不提供 Goal 时，以任务台账状态、执行报告和全局验收作为等价闭环，不得因缺少 Goal 阻断计划执行。
- `blocked`、重试上限和恢复条件应服从当前宿主的实际规则，不把某一客户端的工具协议写成所有客户端的固有能力。

### 4.6 P2：Claude `Edit` 未进入敏感文件提醒

`.claude/settings.json` 的 `PreToolUse` matcher 当前为 `Bash|Write`，`.claude/hooks/pre-tool-use.cjs` 的敏感文件逻辑也只处理 `Write`。因此，使用 `Edit` 修改 `.env.production`、`application-prod.yml`、`credentials.json` 等文件时不会出现提醒。

Claude Code 官方 Hook 文档明确说明工具事件按 `tool_name` 匹配，并使用 `Edit|Write` 作为文件变更示例。参考：[Claude Code Hooks reference](https://code.claude.com/docs/en/hooks)。

这项提醒目前只是安全提示而非硬阻断，所以定为 P2；修复时必须同时调整 matcher 和脚本分支，只改其中一处不会生效。

### 4.7 P3：必需依赖可无绝对上限地突破默认技能数

`router.cjs` 会优先保留全部 `required: true` 依赖，即使超过 `maxSkillsPerTask - 1`。当前 `crud-development` 在同时命中建表、数据权限和多租户条件时，会形成 1 个主技能 + 3 个必需依赖。

这与根规则“最多两个非必需辅助技能”并不冲突，是当前有意保留的逃生机制；风险在于 manifest 未对单个主技能的必需依赖数设置绝对上限。建议增加静态上限或校验规则，防止未来滥用导致上下文膨胀。

### 4.8 P3：双端路由提示格式不一致

- Codex：单行提示。
- Claude：多级 Markdown 标题，并额外展示 `route.reason` 和精确入口路径。

两端功能均正确，目录也分别指向 `.agents/skills/` 与 `.claude/skills/` 或 `.claude/commands/`。这是维护和体验一致性问题，不是功能缺陷。若统一格式，应保留客户端必要的路径差异，不应机械复制字符串。

### 4.9 P3：资料索引固定截断为 16 项

两个拆分脚本都使用 `.slice(0, 16)` 生成二级标题索引。当前实际受影响的入口为：

- 11 个共享技能：`project-migration`、`brainstorm`、`architecture-design`、`exp-sediment`、`task-tracker`、`crud-development`、`ui-mobile`、`utils-toolkit`、`iot-mqtt`、`social-login`、`store-mobile`。
- 3 个命令资料：`init-docs`、`start`、`exp`。

`writing-plans` 当前恰好有 16 个二级标题，尚未发生截断。建议移除固定上限，或在截断时增加“其余章节请查看完整目录”的显式提示，避免入口索引看起来像完整目录。

### 4.10 P3：短入口模板高度同质化

大部分短入口使用相同的“执行边界 / 最小步骤 / 资料索引”模板，领域硬约束主要保留在 YAML 描述和完整资料中。路由依靠 manifest 触发词仍可正常工作，因此这不是错误。

若后续继续优化渐进式披露，可为每个短入口保留 1～2 条最关键的领域禁令或前置条件，使第一层上下文不仅满足形式校验，也能在未加载完整资料前阻止明显误用。

### 4.11 P3：SessionStart 目前只是潜在差异

`.codex/hooks.json` 注册了 `SessionStart → session-start.cjs`，`.claude/settings.json` 没有对应注册。Claude Code 官方协议支持 `SessionStart`，所以技术上可以补齐。

但当前 `.claude/docs/experience/*/*-exp-summary.md` 不存在，Codex 的 SessionStart 脚本也只会返回空结果。因此现阶段没有可观察的功能差异，不能定为 P2 缺陷。应在经验摘要真正启用前决定：双端补齐，或删除无效入口，避免长期保留只有配置没有产物的机制。

## 五、校验盲区

当前校验器擅长发现结构和一致性问题，包括：

- manifest 名称覆盖、路由 fixture 和泛词触发。
- 根规则与模板渲染结果一致。
- 共享技能包递归哈希一致。
- 技能 YAML、BOM、入口行数、`full-guide` 存在性与索引。
- 通过 `skill-check.cjs` 校验全部命令映射正文。

当前仍不覆盖或覆盖不完整的内容包括：

1. 完整资料中的过时治理说明，例如“手改 Hook 技能列表”“手改 AGENTS.md 技能表”。
2. `verify-agent-assets.cjs` 对非 `dev` 命令映射的全量校验。
3. 共享技能依赖的宿主能力是否可用，以及不可用时是否有降级规则。
4. Hook 配置 matcher 与脚本内部 `toolName` 分支是否成对覆盖。
5. 资料索引是否完整，而不仅是入口是否包含 `references/full-guide.md` 字样。

建议将“废弃短语扫描、策略驱动的命令映射遍历、Hook matcher/处理分支一致性”纳入治理校验；宿主能力降级与内容语义仍需要人工评审，不能完全依赖静态脚本。

## 七、总体评估与处理顺序

1. **先修正事实源**：清理两处旧登记说明，并补齐中央校验器对全部命令映射的覆盖。
2. **再统一身份与来源模型**：明确 `framework-sync` 身份，消除命令拆分脚本的静默反向覆盖。
3. **补齐真实安全覆盖**：让 Claude 的 `Edit` 与 `Write` 进入同一敏感文件检查。
4. **完善跨运行时契约**：把 Goal 从“某端专属假设”改为“能力存在则使用、缺失则降级”。
5. **最后处理体验和可维护性问题**：必需依赖上限、提示格式、索引截断、短入口信息密度和 SessionStart 对齐。

最终结论是：**技能治理体系已经从“分散约定”进入“可校验的单源治理”阶段，但尚未完成最后一轮契约收口。当前最值得优先修复的是校验器承诺与实现不一致，而不是继续扩展更多技能或 Hook。**
